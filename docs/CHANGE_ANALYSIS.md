# Module A — Terraform Change Impact Analyzer

## What it does

Parses a saved Terraform plan (as JSON) and produces a report of risk findings, a policy
decision, and a CI exit code. It never runs `terraform apply`, `terraform destroy`, or any
other Terraform command — it only reads the JSON a plan already produced.

## Supported workflow

```bash
cd your-terraform-project
terraform init
terraform plan -out=tfplan
terraform show -json tfplan > plan.json
infraguard analyze-change --plan plan.json
```

A real, runnable example (local-only `random`/`local` providers, no cloud account) lives at
[examples/terraform/sample](../examples/terraform/sample); its `plan.json` was generated by
actually running these three commands against that config, not hand-written.

## CLI and API

```bash
infraguard analyze-change --plan plan.json [--policy policy.yaml] [--format json|markdown|both] [--out DIR]
```

Exit code is the policy decision's exit code (see below) — safe to use directly as a CI gate.

```
POST /api/v1/change-analysis/analyze
{"plan": {...}, "policy": {...}}   # policy is optional; defaults apply if omitted
```

## What is parsed

From each entry in the plan's `resource_changes`:

- `address`, `type`, `name`, `mode` (`managed` or `data`).
- `change.actions` → one of `create`, `update`, `delete`, `replace` (either ordering),
  `read` (data source), `no-op`. Any other combination becomes `unknown` and is surfaced as
  a `parse_warning.unrecognized_action_combination` finding rather than guessed at.
- `change.before` / `change.after`, redacted (see below) before they ever reach a report.
- `change.after_unknown`, flattened into a list of attribute paths whose value is not knowable
  from the plan alone.
- `change.replace_paths`, if present, cited directly in replacement findings.

## Secret redaction

Two independent signals, both applied, because neither alone is trustworthy:

1. Terraform's own `before_sensitive` / `after_sensitive` marks from the plan JSON.
2. A heuristic key-name pattern (`password`, `secret`, `token`, `credential`, `private_key`,
   `access_key`, `api_key`, `connection_string`, `dsn`, `cert`/`certificate`) that catches
   values Terraform did not mark — at the cost of occasionally over-redacting a harmless
   field. Over-redaction is the deliberate direction; a provider failing to mark something
   sensitive is never treated as proof that value is safe to print.

Implementation: [src/infraguard/modules/change_analysis/redaction.py](../src/infraguard/modules/change_analysis/redaction.py).

Redacted `before`/`after` values are surfaced directly in the `destructive_delete` and
`destructive_replace` findings' `evidence` — a reviewer deciding whether a deletion or
replacement is intentional needs to see what's actually changing, and this is the one place
in the report that shows resource attribute values at all. No other rule echoes raw
attribute values, so this is also the only place redaction has anything to redact; it was
verified by hand that a Terraform-marked sensitive field and an unmarked-but-heuristically-
caught one both render as `***REDACTED***` and never as their real value, in both the JSON
and Markdown report (`tests/unit/change_analysis/test_analyzer.py::
test_rendered_report_never_contains_a_raw_secret_value`).

## Resource categories (heuristic, not a provider schema)

Pattern-matched by substring on the resource `type` string
([categories.py](../src/infraguard/modules/change_analysis/categories.py)):

| Category | Example patterns |
|---|---|
| `database` | `db_instance`, `rds_cluster`, `dynamodb_table`, `cosmosdb`, `redshift`, ... |
| `storage` | `s3_bucket`, `storage_bucket`, `ebs_volume`, `disk`, `blob`, ... |
| `iam` | `iam_role`, `iam_policy`, `iam_user`, `service_account`, `role_binding`, ... |
| `networking` | `security_group`, `vpc`, `subnet`, `route_table`, `firewall`, `load_balancer`, ... |
| `compute` | `instance`, `vm_`, `autoscaling_group`, `eks_cluster`, ... |
| `other` | anything that matches none of the above |

**`other` means "no specific rule exists for this," never "this is safe."** A destructive
action on an `other`-category resource still produces a `destructive_delete` /
`destructive_replace` finding, plus a separate `unsupported_resource_type` finding
(confidence `unknown`) flagging the modeling gap explicitly.

This list covers common AWS/Google Cloud/Azure naming conventions and nothing more. It is
not a real provider schema and will misclassify or fail to classify providers/resources it
hasn't seen.

## Dependency graph

Built from the plan's `configuration.root_module.resources[]` block
([dependencies.py](../src/infraguard/modules/change_analysis/dependencies.py)):

- Explicit `depends_on` entries.
- Implicit references Terraform records for each configuration expression (e.g. an
  attribute that interpolates another resource's output).

**Scope, stated plainly: root module only.** A resource addressed `module.x.aws_instance.y`
is not resolved against its child module's configuration — this needs recursive
`module_calls` traversal, which this version does not implement. When any resource address
starts with `module.`, a `module_scoped_dependencies_unsupported` finding says so explicitly,
rather than silently reporting an empty (and misleadingly "safe-looking") dependency set.
**This finding is a stated coverage limitation, not a data problem** — the plan itself is
fine, InfraGuard's view of part of it is just incomplete — so it does not, on its own, trip
the strict policy's fail-closed behavior (see "Policy and CI exit codes" below). This
distinction was added after running a 200-resource synthetic plan through the analyzer:
almost every real Terraform codebase uses child modules, and treating that as equivalent to
malformed input would have made `error` the default outcome for nearly any real plan.

Verified against real Terraform output, not just hand-written fixtures: running the example
in `examples/terraform/sample` correctly recovers both an implicit reference
(`local_file.config` → `random_pet.suffix`, via string interpolation) and an explicit
`depends_on` edge (`local_file.readme` → `local_file.config`).

## Risk rules

Each rule is a pure function of one resource change (plus the dependency graph where
relevant) to zero or more findings — deterministic, no hidden state
([rules.py](../src/infraguard/modules/change_analysis/rules.py)):

| Rule ID | Fires on | Confidence | Notes |
|---|---|---|---|
| `destructive_delete` | any `delete` | confirmed | Severity by category: CRITICAL (database/storage), HIGH (IAM/networking), MEDIUM (compute/other). |
| `destructive_replace` | any `replace` | confirmed | Same severity table. Cites `replace_paths` if the plan reported them; otherwise says plainly that it didn't, and treats the whole resource as at risk rather than assuming a narrow one. |
| `sensitive_category_mutation` | create/update/delete/replace on database/storage/IAM/networking | heuristic | The category match itself is a heuristic — see above. |
| `unknown_after_values` | create/update/replace with unknown-until-apply attributes | confirmed (that it's unknown) | Flags a gap in what can be assessed; never claims those attributes are safe. |
| `unsupported_resource_type` | delete/replace on an `other`-category resource | unknown | States there is no specific rule for this resource type. |
| `dependents_affected` | delete/replace with graph dependents | heuristic | Lists resources that statically reference the one being removed/replaced. |
| `parse_warning.*` | any per-resource parse problem, or a stated coverage limitation | unknown | Turns a skipped/ambiguous input, or a known gap like module-scoped dependencies, into a visible finding, not a silent one. Carries `evidence.fails_closed` (see below) distinguishing the two. |

## Risk score

A single deterministic number: `sum(weight(severity) for each finding)`, capped at 100
(weights: LOW=1, MEDIUM=3, HIGH=7, CRITICAL=15) — see
[risk_score.py](../src/infraguard/modules/change_analysis/risk_score.py). It is **purely
informational** and appears under `report.inputs.risk_score` with its own explanation
string. **It never drives the policy decision** — only explicit severity thresholds over
findings do. This is a direct requirement from the project brief: a numeric score must never
itself approve or reject a change.

## Policy and CI exit codes

Configured via [policy.py](../src/infraguard/modules/change_analysis/policy.py) /
`examples/policies/*.yaml`:

| Setting | Default | Meaning |
|---|---|---|
| `fail_on_severity_at_or_above` | `high` | Any finding at/above this severity → `fail` |
| `warn_on_severity_at_or_above` | `medium` | Any finding at/above this severity (below fail) → `warn` |
| `strict_on_parse_warnings` | `true` | Any *fatal* parse warning → `error`, regardless of other findings |

A `parse_warning.*` finding is only "fatal" for this purpose if its underlying
`ParseWarning.fails_closed` is `True` (the default). It's `False` for a handful of known,
stated coverage limitations — currently just `module_scoped_dependencies_unsupported` —
where the input is valid and InfraGuard's analysis of it is simply incomplete in a
documented way. Those still appear as ordinary MEDIUM findings (so they're never silently
dropped), they just don't force the harsher `error`/exit-2 outcome on their own; a genuinely
malformed resource entry (missing `address`, an invalid `change` block, etc.) always does.

Decision precedence (first match wins) and CI exit codes:

1. **`error`** (exit 2) — `strict_on_parse_warnings` is true and at least one *fatal*
   `parse_warning.*` finding exists. **This is the "never fail open on invalid input"
   guarantee**: genuinely incomplete/malformed input always fails closed here, never
   silently passes — but a stated coverage limitation on otherwise-valid input does not,
   by itself, trigger this.
2. **`fail`** (exit 1) — at least one finding at/above `fail_on_severity_at_or_above`.
3. **`warn`** (exit 0) — at least one finding at/above `warn_on_severity_at_or_above`.
4. **`pass`** (exit 0) — no findings at or above the warning threshold.

The policy decision always names the specific finding IDs that triggered it
(`triggered_finding_ids`) — never an unexplained pass/fail.

## Input validation

- Plan files over 25 MB are rejected outright (`MAX_PLAN_SIZE_BYTES` in `analyzer.py`).
- A plan JSON root that isn't an object, or that lacks a `resource_changes` list entirely, is
  a **fatal** `InputValidationError` — there is nothing safe to report on.
- A malformed individual `resource_changes` entry (missing `address`, `type`/`name`, or
  `change`) is **recoverable**: it's skipped and recorded as a `parse_warning.*` finding,
  which the default strict policy turns into an `error` decision rather than ignoring it.

## Known limitations (stated, not hidden)

- Dependency resolution is root-module only (see above).
- Resource category detection is a naming-pattern heuristic across common providers, not a
  real schema for any of them.
- `after_unknown` attributes genuinely cannot be assessed from a plan alone — the tool says
  so rather than guessing.
- No understanding of actual IAM policy semantics, network reachability, or live cloud
  state — this is a static analysis of one JSON document.

## Test fixtures

`tests/fixtures/change_analysis/` contains hand-crafted plan JSON covering: create, update,
delete, both replace orderings (with and without `replace_paths`), no-op, a data-source
read, an explicit+implicit dependency chain, nested unknown values, Terraform-marked and
heuristically-detected sensitive values, an unsupported resource type, a module-scoped
resource (incomplete dependency info), and multiple malformed-input shapes (missing
`resource_changes`, a non-object root, a resource entry missing its address, invalid JSON
syntax). Each has a corresponding test in `tests/unit/change_analysis/`.
